# Loss recovery, reordering, and MTU evidence

This is a read-only review of retained REA/Ghidra output for installed `speedify.exe` 17.2.1.13911, SHA-256 `0098d5e1a34025c5b623f719934d457d324215f4c90a5491d2c1af98c30cc4f8`. It neither executes Speedify nor changes GameBond or the live network. Function addresses identify analyzed procedures; recovered names/types and the interpretations below are not original source. Batch Evidence IDs in each exported function identify the retained records.

## Correction to the earlier recovery attribution

The earlier ledger associates `0x14045e15c` with buffered packet retransmission. Both its prior Evidence `ev_df18b05920b9f0f5203ba040787197bf63bb77a701c91f6cbce9efcb56b67623` and the full-export [function](../evidence/full/speedify.exe/pseudocode/0x14045e15c.c) show a `CreditFailoverBlock` callback wrapper referencing `multiflowcodelqueue.cc`. The wrapper selects callback `0x14045ee00`; that [callback](../evidence/full/speedify.exe/pseudocode/0x14045ee00.c) writes two supplied values and a time-related field under a lock. Full-export Evidence for both is `ev_5fd579af1683e322e9c67cab23361a40638ffaf4977d508cb3cb1803e6d09310`.

This was an incorrect summary of the retained function, not evidence of a changed binary or a new selector mapping. The direct buffered-retransmission evidence is at the separate procedures below.

## Reordering has distinct delivery policies

[0x14041dfee](../evidence/full/speedify.exe/pseudocode/0x14041dfee.c), Evidence `ev_5679540b84547d04bc304554b40388c242f680bdde33f912e174e11393d96329`, has separate branches for duplicate flow starts, the next expected sequence, newly inserted packets, and a late recovered packet. It compares both sequence ordering and transmission-time ordering. A guarded branch returns a distinct delivery status and updates delivered transmission time for a late recovered packet. This is stronger evidence than simply finding a reordering class name.

[0x14041e9a0](../evidence/full/speedify.exe/pseudocode/0x14041e9a0.c), same Evidence, delivers the next sequence promptly. For a packet beyond a gap it either initiates gap handling or, under a separate policy flag, releases past the gap once packet age meets the wait timeout or a fixed-delay due condition applies. [0x140420822](../evidence/full/speedify.exe/pseudocode/0x140420822.c), same Evidence, separately detects lack of forward progress for the supplied timeout and marks a stuck flow. [0x14041ef30](../evidence/full/speedify.exe/pseudocode/0x14041ef30.c), same Evidence, computes when to revisit the queue, including remaining wait time rather than a universal fixed delay. Exact policy flag meanings and timer defaults remain partly inferred.

GameBond's current replay bitmap accepts reordered authenticated packets once and delivers them immediately. It does **not** put packets back into per-flow sequence order, detect per-flow loss ranges, send recovery feedback, or deliver an unavailable-packet control message. Its one transport sequence space also includes probes and unrelated flows; a gap in that global sequence is therefore not a reliable per-game packet-loss signal. These capabilities would require an independent data/flow sequence design rather than treating replay-window gaps as NACKs.

For gaming, retain immediate first-arrival delivery by default. A short, bounded, per-flow ordering window is an optional experiment for flows where reordered delivery demonstrably hurts. Its timer must expire without blocking unrelated game flows or bulk traffic. Fixed-delay buffering and waiting a complete slow-path RTT are unsuitable defaults for the stated low-latency objective; that is a design assessment, not a recovered Speedify guarantee or a measured CoD tolerance.

GameBond currently has a configured inner MTU and a fixed outer overhead calculation, rejects oversize payloads, and counts send errors. It does not establish the usable path MTU separately on 5G and Starlink or negotiate changes. A future implementation should authenticate candidate/response association, enforce sane bounds, account for its own protocol overhead, and handle a payload too large for one redundant path without silently assuming both copies can travel. A fixed conservative MTU remains a deliberate initial configuration until this is measured.

## FEC and ACK coverage remain unresolved

A bounded search parsed quoted string literals in all 19,882 successfully exported procedure files. It found **zero** matching literals for the case-insensitive whole-token patterns `fec`, `parity`, `erasure`, `reed.?solomon`, or `forward.error.correction`. Evidence IDs and function-address hex were excluded by searching only quoted literals. This search does **not** prove absence of FEC: relevant code may lack these strings, use another name, lie in one of four failed procedures, or exist server-side outside the supplied daemon.

The inspected branches establish loss ranges, requests, buffered retransmission, retry limits, and unavailable feedback. They do not establish a complete positive ACK/SACK protocol, FEC matrix, block size, coding rate, or repair-symbol generation. Do not claim Speedify FEC was recovered or copy an assumed coding scheme into GameBond on this evidence.

## Suggested implementation order

1. **Observe per-flow delivered loss and recovery usefulness.** Add separate data/flow sequences and authenticated bounded feedback, with counters distinguishing first-arrival loss, recovered-before-deadline, recovered-too-late, and unavailable. Keep the existing anti-replay sequence independent. This provides evidence to decide whether ARQ helps instead of counting only duplicate copies or ping responses.
2. **Add per-path MTU discovery and error feedback.** The retained daemon has concrete negotiation and fallback behavior, while GameBond currently has fixed configuration. Test asymmetric path limits and MTU changes with one path interrupted; a healthy small probe must not imply full game-sized datagrams fit.
3. **Add bounded, deadline-aware recovery as an opt-in policy.** A sender cache needs a byte/packet/age limit; requests need rate/size limits, retry budgets, expiry, and explicit unavailable responses. Prefer another usable path when it can meet the remaining budget. Earliest useful recovery is approximately gap-detection wait plus feedback travel plus retransmission travel; using one symmetric path, the latter two are roughly one RTT. At the previously reported elevated RTTs, recovery may arrive far too late for a short deadline. The actual CoD packet deadline is unknown and must be measured; do not set it from Speedify's counters or scheduling values.
4. **Experiment with a small per-flow reorder window only when beneficial.** Bulk TCP and latency-sensitive UDP can need different policies. TCP already has its own reliability and ordering; an outer ARQ layer can add redundant work, reordering delay, and feedback traffic. Compare measured goodput, inner retransmissions, game gap tails, and queue age before enabling either policy broadly.
5. **Treat FEC as a separate original experiment.** First establish that simultaneous useful game-packet losses remain after priority/pacing/duplication fixes and whether feedback is too slow. The supplied code review does not establish a Speedify FEC design.

The existing [reconstruction ledger](reconstruction.md) records four failed procedures, missing original types, and a non-return inference issue that can truncate caller tails. Those limits apply to every row here. None of this review establishes Speedify server source, protocol compatibility, live execution of these branches, or a no-disconnection guarantee.
