# Scheduling, congestion and bonding analysis

Read-only review of the retained Speedify 17.2.1.13911 daemon export, SHA-256 `0098d5e1a34025c5b623f719934d457d324215f4c90a5491d2c1af98c30cc4f8`. No networking, running process, client or server was changed. This is static evidence and an engineering proposal, not measured behavior or original source. See [the main channel-bonding review](channel-bonding-review.md) and [export limitations](reconstruction.md).

REA MCP imported and validated the full 623-record canonical bundle. `get_evidence_bundle` with summary and the exact bonding Evidence ID returned a retained complete record for the matching target. `inspect_analysis_view` explicitly does not support `batch_decompile`, and record filters on `get_evidence_bundle` require summary mode. Consequently, the already retained per-function bodies were read locally; no new Ghidra session was launched. Initial searches matched quoted network terms, then followed concrete callees and state updates rather than treating a string hit as proof.

## 1. Packet-level, weighted connection selection

**Observed.** [0x140296d36](../evidence/full/speedify.exe/pseudocode/0x140296d36.c), in `SpeedifyTransportChannel::SendPacket`, calls [0x14028334c](../evidence/full/speedify.exe/pseudocode/0x14028334c.c) before attempting the selected connection. The latter clears the selected connection at channel offset `0xc60`, builds/filters candidate vectors, invokes the chooser's first virtual slot with a candidate list and packet-derived argument, and stores its result at `0xc60`. The send path then checks that connection's eligibility and calls [0x14029573c](../evidence/full/speedify.exe/pseudocode/0x14029573c.c) with the current packet and selected connection; retry paths can prepare another choice. This is a concrete per-packet scheduling seam.

[0x14035e286](../evidence/full/speedify.exe/pseudocode/0x14035e286.c) computes eligible-link weights, sums them, samples a random value divided by 32767, and subtracts each link's normalized weight until selecting a candidate. Its helper [0x14035e0f6](../evidence/full/speedify.exe/pseudocode/0x14035e0f6.c) uses bandwidth-like getters and reduces weight when a latency getter exceeds a minimum-like getter by more than 100 in the shown branch. [0x140360696](../evidence/full/speedify.exe/pseudocode/0x140360696.c) constructs different chooser implementations by mode; [0x1402982b4](../evidence/full/speedify.exe/pseudocode/0x1402982b4.c) names Round Robin, Lowest Latency, Minimax, Variable Minimax, Redundant, Speed and Streaming modes.

**Inference / unknown.** There is stronger evidence here than a per-flow load balancer: the chooser is invoked in the packet send preparation path. However, every virtual dispatch and return tail has not been resolved. No runtime capture proves that successive packets of one particular inner flow used different physical links. The weighted routine's active mode and actual field units are not fully established. This review therefore does not claim fully reconstructed single-flow striping or a demonstrated summed bandwidth result.

**GameBond gap / proposal.** Current nonreplicated `Node.send` uses healthy-path flow affinity, initially selected by RTT. A single bulk flow stays on one path. After delivery-rate and in-flight feedback exist, add a separate bulk mode that selects a path per packet using available byte budget and predicted arrival time. Keep selective game duplication immediate. A bounded, per-flow receiver reorder policy would be needed for useful TCP striping; game delivery must not wait on that reorder queue. Priority: **P1 after feedback/pacing**, substantial work.

## 2. Per-link capacity discovery, pacing and congestion windows

**Observed.** Connection latency processing [0x140439d44](../evidence/full/speedify.exe/pseudocode/0x140439d44.c) feeds measurements into [0x140517368](../evidence/full/speedify.exe/pseudocode/0x140517368.c). That controller updates sample counts/sums/minima/maxima and related RTT filters. The retained controller code contains the source path `bbrcongestioncontrol.cc`, but the evidence is not just the filename:

* [0x140514e7a](../evidence/full/speedify.exe/pseudocode/0x140514e7a.c) has actual state-dependent transitions labelled STARTUP, DRAIN, PROBE_BW and an RTT probe. In one established-estimate branch, a discrepancy greater than 0.2 combined with a bandwidth-like value above 1,250,000 calls a startup-reset routine. Another branch enters an RTT probe after a 10,000-unit interval. A raised minimum-like estimate can cause rediscovery.
* [0x1405147e0](../evidence/full/speedify.exe/pseudocode/0x1405147e0.c) writes the controller state, changes gain fields and calls both window and pacing recalculation routines.
* [0x140514c50](../evidence/full/speedify.exe/pseudocode/0x140514c50.c) computes a congestion-window-like value from estimates/gains, applies bounds and includes a branch limiting a decrease to half the preceding value before further mode adjustments.
* [0x140514d8a](../evidence/full/speedify.exe/pseudocode/0x140514d8a.c) calculates another rate-like field from an estimate and gain, with a shown lower bound of 10,000 in one enabled branch; a locked-rate mode uses a stored configured value instead.
* [0x14043b748](../evidence/full/speedify.exe/pseudocode/0x14043b748.c) updates locked send bits-per-second state and passes a right-shift-by-three rate to the controller. The diagnostic [0x14027f806](../evidence/full/speedify.exe/pseudocode/0x14027f806.c) reports distinct in-flight bytes, congestion window, pacing bytes, pacing rate, receive/send locked rates and RTT quantities.

**Inference / unknown.** This is a model-based internal controller with capacity probing, bounded rate/window updates and adaptation after changing conditions. It is not evidence that the exact Linux BBR1/2/3 algorithm was recovered, nor proof that all units/defaults are known. The virtual send-gate relationship and controller calibration remain incomplete.

**GameBond gap / proposal.** GameBond already has a configured bulk token bucket; generic pacing is not missing. What is missing is authenticated, direction-specific per-path delivery-rate/in-flight feedback and an adaptive per-link budget. Add those before removing a conservative bulk cap or attempting aggregation. Distinguish unique delivered payload from duplicate copies in measurements. Start with bounded rate changes, small controlled probes, and a game-traffic byte reserve; a full BBR reconstruction is not required for the first useful improvement. Priority: **P0/P1 foundation for throughput bonding**, high value and significant validation work.

Controller Evidence: `ev_02f895e1abb2fa1c38ea0513f5066d727cd118e6797ce5ee985aec1859feae67`; sample path: `ev_073d16a559f0bbd275b9d095ea2332c6729ae54d12d35e0c8eb1fdfee764c527`; connection samples: `ev_55675574adfb03e22a734959f6d6be5ebaea46f09772c9b715d0905aa795254d`; locked-rate setter: `ev_654b82d999dcbe967882e9f8811976caf5817f908e3a040cbf0599c09e3711cb`. Constants above are observations from particular branches, not proposed GameBond settings.

## 3. Byte-fair flow queues and bounded scheduler work

**Observed.** [0x14045c566](../evidence/full/speedify.exe/pseudocode/0x14045c566.c), in the multiflow queue subsystem, adds a configurable quantum to per-flow deficit state at `flow+0xc0`, caps it, checks whether the head packet fits, passes a byte budget to dequeue, and subtracts served bytes from that deficit. It rotates candidates through separate active lists via [0x14045cc3e](../evidence/full/speedify.exe/pseudocode/0x14045cc3e.c). In its insufficient-budget branch it bounds iterations by `2 * flow_count + 10`. It records packet residence averages and maxima rather than inferring queueing from RTT alone. [0x14045d6a2](../evidence/full/speedify.exe/pseudocode/0x14045d6a2.c) sets the quantum, including a 500-unit branch and a separately capped deficit allowance.

**Inference / unknown.** This is consistent with deficit-round-robin-style byte fairness over flow queues, with separate priority behavior. Exact whole-system fairness and all flow-to-queue mappings have not been reconstructed; the iteration bound is specific to the shown branch.

**GameBond gap / proposal.** The optimized scheduler is bounded and gives packet-count fairness between two classes, but it still has FIFO ordering inside each class. One large bulk flow can get ahead of DNS or another small nonpriority flow; packet-count service also treats small and MTU-sized datagrams equally. Reuse the already available canonical flow key for bounded per-flow bulk queues and byte-deficit service, with a strict work budget before yielding. Keep the direct gameplay path outside bulk arbitration. Priority: **P1**, moderate implementation work with deterministic fairness and burst tests.

Evidence for the scheduler, candidate selection and quantum setter: `ev_5b5af77d3d24bb0fdfaf67238f0472b2a6a1a7e146d97ad08e4e92a1f76a340a`.

## 4. Controlled queue delay and pressure drops from the largest bulk queue

**Observed.** [0x1405235ff](../evidence/full/speedify.exe/pseudocode/0x1405235ff.c) computes packet age from a timestamp and adjusts it by bounded ancillary delays, clamping below zero. [0x140523bbe](../evidence/full/speedify.exe/pseudocode/0x140523bbe.c) compares that result with queue thresholds and includes a backlog condition above `0x1000` bytes. [0x1405230dc](../evidence/full/speedify.exe/pseudocode/0x1405230dc.c) maintains persistent dropping state; it schedules the next action using `interval / sqrt(drop_count)`, increments the count on subsequent actions, and exits dropping when the condition clears. [0x1405237ba](../evidence/full/speedify.exe/pseudocode/0x1405237ba.c) invokes that state machine and repeatedly removes packets when instructed. These are concrete CoDel-style mechanics; the recovered source path also names `codelqueue.cc`.

Separately, [0x14045b9a4](../evidence/full/speedify.exe/pseudocode/0x14045b9a4.c) searches for the largest eligible queue. [0x14045b614](../evidence/full/speedify.exe/pseudocode/0x14045b614.c) uses that search under packet-pool pressure and calls the drop path, with reason `pool pressure (largest queue)`. [0x14045bae8](../evidence/full/speedify.exe/pseudocode/0x14045bae8.c) selects a pressure victim, prefers avoiding the previously chosen queue when another candidate exists, and drops with reason `priority congestion`. Queue totals and drop counters are updated afterward.

**Inference / unknown.** This actively controls persistent queueing, rather than waiting only for a full queue or a fixed packet lifetime. Exact target/interval defaults, all eligibility conditions and ECN support are not established here. Do not copy opaque thresholds or claim a standards-complete FQ-CoDel reconstruction.

**GameBond gap / proposal.** Current TTL/full drops are useful safety bounds, but there is no persistent-delay controller or per-flow pressure victim selection. After per-flow queues exist, expire/drop bulk from the longest problematic queue and expose separate age, admission and pressure-drop counters. Add controlled queue-delay feedback to bulk pacing. Keep game packets protected from bulk pressure decisions; do not add a fixed game jitter buffer. Priority: **P1**, moderate work after flow isolation.

Core age/control/drop-loop Evidence: `ev_ce6883ba52a4cf05587680e5a7180d3efe91473a1ba8a0e706024e307cb6b47c`; explicit drop wrapper: `ev_6726ae84e48fb0924486f6a4faa4c88abf45d3133f01b963111a396e7c360e36`; largest-queue/priority-pressure mechanisms: `ev_5b5af77d3d24bb0fdfaf67238f0472b2a6a1a7e146d97ad08e4e92a1f76a340a`.

## 5. Useful-link filtering and latency hysteresis

**Observed.** [0x14035feb0](../evidence/full/speedify.exe/pseudocode/0x14035feb0.c) returns a score formed from latency divided by 1000 plus a packet-sized argument divided by a bandwidth-like rate times `1,000,000 * 0.125`. Some degradation branches increase that score. [0x14035f5d4](../evidence/full/speedify.exe/pseudocode/0x14035f5d4.c) compares link scores, uses a 0.9 factor for an already filtered link, applies a bandwidth ratio involving 8.5, removes filtered candidates, and unfilters a sole remaining candidate. Its all-filtered fallback clears filtering. Filtering-duration helpers accumulate elapsed filtered time.

[0x140434b76](../evidence/full/speedify.exe/pseudocode/0x140434b76.c) separately compares packet-like and socket-like latency, increments a persistent divergence counter only while conditions hold, and resets it when they clear. One threshold computation ranges from 3 to 12 observations; call cadence is not established, so this is not a universal 3-12 second failover claim. [0x140439d44](../evidence/full/speedify.exe/pseudocode/0x140439d44.c) can discard a latency sample above 1000 under a specific stale/high-delay state, rather than applying every sample indiscriminately.

**Inference / unknown.** The score is consistent with predicted arrival/transfer completion, and the 0.9 branch supports hysteresis rather than rapid toggling at one boundary. This does not mean an expensive/high-RTT link should always be disabled: the fallback logic preserves a remaining path, and the game duplication policy is a separate decision. Full mapping to every public slow/poor/bonding-filtered statistic remains incomplete.

**GameBond gap / proposal.** Current health expiry and smoothed RTT do not distinguish a merely slow bulk path from an unusable one, or baseline propagation delay from load-induced queueing. Add separate health, capacity and usefulness states, a bounded baseline/minimum and robust delay samples, and recovery hysteresis. Filter unhelpful links for bulk while keeping them probed and eligible for deliberate gameplay redundancy. Priority: **P1 after trustworthy feedback**, moderate work; never derive universal thresholds solely from these literals.

Bonding score/filter Evidence: `ev_d571ae777e00b63ea5778ed1a54ad79939517d5ea07a73cf8fb2b8c04a165e0a`; divergence counter: `ev_a95ab895d6000f0b00b72baea1f5ef044ec57761c3598411ef5c70773c0c41e2`; sample filtering: `ev_55675574adfb03e22a734959f6d6be5ebaea46f09772c9b715d0905aa795254d`.

## SDK version boundary and confidence

The [official release notes](https://speedify.github.io/speedify-sdk-docs/desktop/whatsnew.html#whatsnew_1721), retrieved 2026-11-02, describe 17.2.1 as expanding kernel TCP CCA choices; the 16.8 entry identifies the underlying TCP, multi-TCP and HTTPS/WebSocket sockets. That API is separate from the internal `bbrcongestioncontrol.cc` implementation above. The notes also distinguish public bonding/poor flags (16.5), a sustained filtered/low-throughput indicator (16.9), and removal of an unreliable peak-only bonding-benefit measure (17.1). Those documentation entries neither date the recovered internal algorithms nor prove UDP uses a chosen kernel TCP CCA. No earlier binary was supplied for version comparison.

The no-return inconsistency around `FUN_140593df0` affects many emitted caller tails, and numerous calls remain virtual. Success means a decompiler emitted text, not that every branch or return was recovered. In particular, per-packet selection is observed, but a complete end-to-end same-flow striping/reassembly proof remains unresolved. A practical bandwidth claim needs controlled, bidirectional goodput measurements with matched single-link baselines, stable packet-gap/gameplay measurements, and explicit duplicate overhead; summing interface byte counters is insufficient.
