Review date: 2026-11-02. Target: installed Speedify 17.2.1.13911 daemon, x86-64, SHA-256 `0098d5e1a34025c5b623f719934d457d324215f4c90a5491d2c1af98c30cc4f8`.

The retained REA/Ghidra export attempted 19,886 discovered internal procedures: 19,882 emitted pseudocode and four failed explicitly. The inventory also contains 397 external imports. This is recovered pseudocode, not original source, an exhaustive proof of executable semantics, or a working proprietary protocol specification. The full export, batch Evidence IDs, failures, and non-return/control-flow limitation are documented in [reconstruction.md](docs/reconstruction.md).

The user's target is two distinct behaviors sharing one stable VPS exit: immediate selective duplication for CoD, and packet-level aggregation for a single bulk transfer. Keeping each bulk flow on one link protects ordering but cannot aggregate that one transfer. Duplicating all bulk packets consumes both paths without adding unique delivered throughput. Interface byte totals must therefore distinguish useful payload from duplicate/probe overhead.

## Original GameBond design and implementation status

GameBond uses an independent authenticated protocol between our Windows client and VPS. Its keys, nonce domains, anti-replay window, data-flow sequence format, queue limits, pacing gains, reorder timeout, and future feedback scheme are our design choices. They are not recovered Speedify constants and do not establish Speedify compatibility.

GameBond 0.3.0 implements the following original design. Legacy GB01 mode remains compatible with the existing running pair; opt-in GB02 bonding requires a matching client and server and a fresh shared session. Source changes do not upgrade a running process.

| Work | Status and rationale |
| --- | --- |
| Preserve selective game duplication and immediate delivery | Implemented and verified in both directions. Replicated gameplay bypasses pacing and bulk reordering. |
| Independent per-flow data sequence | Implemented: each striped packet carries a random flow ID, independent 64-bit flow sequence, and sender path epoch. Encryption replay sequences remain independent and also cover control traffic. |
| Bounded reorder component | Integrated in [gamebond/transport.py](gamebond/transport.py) using [gamebond/reorder.py](gamebond/reorder.py). The default 30 ms is an original opt-in bulk policy, not a recovered CoD tolerance. Lost gaps release at the deadline; this does not recover missing payloads. |
| Reorder resource behavior | At most 1,024 tracked flows, 2,048 retained packets, and 4 MiB retained payload; defaults are configurable. Expected packets release immediately. Packet/byte pressure forces a gap forward; flow eviction or 120-second idle expiry records explicit drops. Missing 64-bit ranges use arithmetic, avoiding a loop over missing sequence numbers. Priority bypass belongs to the caller. |
| Packet-level bulk striping | Implemented in both directions. One bulk flow can use every healthy path, chosen per packet using readiness and predicted arrival time. No healthy path returns a counted application drop; pacing waits outside the transport lock and has a 200 ms send deadline. |
| Per-path adaptive pacing and in-flight accounting | Implemented in [gamebond/bonding.py](gamebond/bonding.py): conservative original AIMD, authenticated cumulative byte feedback, bounded pending metadata and byte windows, delay/timeout backoff, utilization-gated additive growth, and at most 2 ms of late pacing credit. This is not a BBR reconstruction. |
| Feedback and NAT recovery | Cumulative feedback is batched at 20 ms and repeated at 100 ms when needed. An authenticated path epoch migrates logical path state across source endpoint changes; delayed older packets cannot move it back. Replay, epoch and counter validation precede budget credit. |
| Byte-fair per-flow bulk queues and pressure behavior | Further work. The current application scheduler remains bounded priority/normal queues; this update does not claim a complete deficit-round-robin or FQ-CoDel implementation. |
| Deadline-aware ARQ, dynamic path MTU, and FEC | Further work, not implemented by the reorder component. Recovery requires bounded sender retention, authenticated/rate-limited feedback, unavailable responses, and a demonstrated remaining delivery budget. FEC requires a separately justified original design. |

## Validation needed before throughput claims

Compare each physical link alone with both links together for one bulk stream and parallel streams, independently upstream and downstream. Record unique useful throughput, per-path wire bytes, delivery-rate estimates, queue residence, loss, reorder depth/wait, and game packet-gap tails while downloads run. Repeat physical interruption/recovery of each link and changes in latency/capacity. A controlled UDP echo measures probe delivery; it does not establish CoD's kick threshold.

Aggregated useful throughput is limited by path asymmetry, protocol overhead, the VPS, remote service, and receiver behavior. Summing interface byte counters or duplicating bulk packets is not evidence of speed aggregation. No no-disconnection guarantee follows from static analysis or a successful loopback test.

## Implemented log attachment

The launcher tees client stdout/stderr to an authenticated TCP relay on `127.0.0.1`. Attachments are read-only. Separate authenticated controls allow only `stop`, `restart` and `status`; they cannot submit shell commands, paths or arbitrary input. A persistent elevated supervisor performs cooperative cleanup/restart, while the operator connects without elevation. The relay has a 256 KiB replay ring, bounded publisher/reader queues, an eight-attachment limit, and one owner slot to prevent duplicate supervised clients. Connection metadata is private runtime state at `.runtime/tty-session.json`; tokens are not printed in logs. Attach without elevation with:

```powershell
python -m gamebond.tty_server attach --tail 100 --duration 30
python -m gamebond.tty_server -stop
python -m gamebond.tty_server -restart
python -m gamebond.tty_server -status
```

The relay was started and successfully attached to under the non-elevated agent token. Existing already-running clients cannot retroactively publish their old console output; logging starts when launched through the updated script.

## Probe-loss detection latency (this revision)

Confirmed from source: before this change `Node._probe` counted a probe as lost only after `path_timeout` (2.0 s by default) while probes are sent every `probe_interval` (0.25 s). `AdaptiveQoS.observe` consumes `probe_quality.lost` as its only loss signal when no bulk ACKs are flowing, so a lossy episode on a single-copy call/stream flow was seen roughly two seconds late and the redundancy window opened after the damage.

Change: a probe is now declared lost as soon as a probe sent *after* it on the same path has been answered and it has aged past `max(100 ms, 2*srtt + 4*jitter)` (capped at half of `path_timeout`). A reply that still arrives is reclassified from lost to `late` and continues to feed the RTT/jitter estimate; previously it was accepted only inside the 2 s window, and an early declaration that discarded it would have hidden exactly the delay spikes that jitter tracking needs. New counters `lost_early` and `late` are exposed under `probe_quality`. The 2 s timeout still governs a path with no later reply. Unit tests: `tests/test_probe_loss.py` (deterministic clock; overtaken probe, late-reply reclassification, tight-spacing guard, cross-path reply rejection).

Not established: no live or physical-link measurement was taken. Detection latency is bounded by design at about one probe interval plus the guard (roughly 0.3-0.5 s at defaults), not measured on 5G or Starlink. Probes remain round-trip samples, so they cannot attribute loss to upstream or downstream, and they are not a measure of game-packet loss. `AdaptiveQoS` thresholds (2 % loss, 8 ms jitter, 3 s hold) were not retuned.

## Data-plane loss evidence, deadline-aware repair and per-path MTU

Implements steps 1-3 of the suggested order in [analysis-recovery.md](docs/analysis-recovery.md). These are original GameBond designs informed by the retained Speedify evidence (range-based gap requests, explicit unavailable feedback, `0x21`-`0x24` MTU probe/response/decision/update messages, stepwise fallback). They are not Speedify wire formats or recovered constants.

**Wire compatibility.** Five new authenticated message kinds (`DATA_COPY` 13, `MTU_PROBE` 14, `MTU_ACK` 15, `REPAIR_NA` 16, `COPY_REPORT` 17). A bonded receiver accepts all of them always; a sender emits them only when the option below is on (`REPAIR_NA` only in answer to a `REPAIR`). A peer built before this change drops them as malformed, so **upgrade the server first**, then enable options on the client. Legacy GB01 mode is unchanged and the options require `bonding_mode`. All three options default off.

| Option | Effect | Evidence it produces |
| --- | --- | --- |
| `loss_tracking` | Replicated gameplay is sent as `DATA_COPY` (same payload, same delivery path, same transport sequence on every path). The receiver records which expected paths delivered each sequence within a resolve delay (`max(50 ms, path skew + 4*jitter + 20 ms)`, cap 250 ms) and reports cumulative counts back every 0.5 s. | Per path `copy_quality` (received here: seen / missed / late / arrival lag behind the fastest copy) and `peer_copy_quality` (how *my* copies fared at the peer, the direction a sender can act on). `AdaptiveQoS` turns `copy_loss` into a redundancy reason once at least 8 comparisons exist in an observation. |
| `repair_deadline_ms` (default 250) | A bulk gap is repaired only if time already spent behind the hole plus the best path's RTT fits the deadline. An unmeasured RTT does not block a repair. A sender that no longer holds the packet answers `REPAIR_NA` and the receiver stops asking. | `repair_skipped_deadline`, `repair_unavailable_sent` / `repair_unavailable`, `gap_filled_in_time` / `gap_filled_late` (gaps we asked about that were filled by either the original or the repair). |
| `path_mtu_discovery` | Each path searches its outbound datagram size with padded authenticated probes over a fixed ladder up to the configured MTU, with don't-fragment set (Linux `IP_MTU_DISCOVER`, Windows `IP_DONTFRAGMENT`). Copies larger than a path's discovered size go to other paths when one fits; otherwise they are still attempted. | Per path `mtu` (`path_mtu`, `capable`, failed sizes, `df_enforced`, `skips`). A peer that never answers leaves the configured MTU unchanged, so an old peer cannot shrink a path. |

**Limits, stated plainly.**
- `repair_deadline_ms` default 250 is an assumption, not a measured inner-TCP retransmission timeout or a Call of Duty packet deadline. Tune it from `gap_filled_late` versus `gap_filled_in_time`.
- Copy accounting cannot see a packet lost on *every* path, and "missed" means "absent at the resolve delay"; a copy that arrives afterwards is reclassified `late`. When replication is off there are no copies and no evidence, so redundancy driven by copy loss can lapse while the link is still lossy; probe loss then re-arms it.
- The expected-path set is the receiver's view of ready, enabled paths; a sender that excluded a path for a reason the receiver cannot see would show that path as missing.
- MTU discovery measures the outbound direction of each node only. The inner tunnel MTU is still one configured number: a path whose discovered size is below it is avoided per packet, not fixed, so lower `mtu` if `mtu.path_mtu` stays under the configured size. If `df_enforced` is false the platform call failed and a probe answer does not prove the datagram was not fragmented.
- Verified only by unit tests and loopback tests with software-injected drops (`tests/test_path_quality.py`, `tests/test_data_plane_quality.py`, `tests/test_adaptive_qos_copy_loss.py`). No 5G/Starlink measurement, no server deployment and no live Call of Duty result exists for any of this.


## Sender-driven failover replay (`failover_replay`)

Speedify's failover chain (`0x14028f9d4` -> `0x140424d64` -> `0x140299434`, see [analysis-recovery.md](docs/analysis-recovery.md)) takes the packets buffered for a failed connection and retries them on another one, without waiting for the receiver. Before this change GameBond learned of a dead path only after `path_timeout` (2.0 s default): early probe-loss detection needs a *later* probe on the same path to be answered, which cannot happen on a dead link. For that window the striper kept writing bulk into the dead path, and recovery depended on the receiver noticing a gap. That never happens for a **tail** loss (nothing follows the lost packet) or for non-TCP bulk, which the receiver never asks to repair.

Original GameBond design, opt-in (`failover_replay`, default off, requires `bonding_mode`). **No wire change**: replays are ordinary `STRIPED` packets with the original flow and sequence, so no peer upgrade is needed and the receiver's existing duplicate suppression absorbs any packet that had already arrived.

- **Suspicion.** A path is suspect after `min(path_timeout/2, max(2.5*probe_interval, 4*srtt + 8*jitter))` without any authenticated packet (about 0.625 s at defaults, against 2.0 s). Stats show per-path `suspect`; counters `failover_suspected`, `failover_recovered`.
- **Avoidance.** Bulk striping skips suspect paths while at least one other path is alive; a sole path stays usable. Probes and replicated gameplay still use a suspect path, so recovery is noticed.
- **Replay.** On the healthy-to-suspect transition, cached bulk packets last sent on that path since it last proved alive (less one RTT) are queued, up to 512, and re-sent on the best live path, paced by that path's budget, 16 per maintenance tick. Counters `failover_replayed`, `failover_replay_dropped` (evicted, older than 1 s, or already moved by a receiver repair).
- **Cache.** With the option on, the existing bounded repair cache (2,048 packets, <= 2 KiB payload, 1 s) also keeps non-TCP bulk, and each entry records the path it last used.

Tests: [tests/test_failover_replay.py](tests/test_failover_replay.py), real loopback sockets with one path blackholed in both directions. A negative control with the option off confirms the tail packet is lost; with it on the packet is delivered (25 of 25 repeated runs).

**Limits.**
- A replay is not a deadline guarantee. It arrives at least one suspicion interval (about 0.6 s at defaults) after the original, so it recovers a TCP/QUIC bulk segment but not a real-time game packet; gameplay continuity during an outage still relies on replicated copies.
- Replayed packets can arrive after the reorder deadline (30 ms) and are delivered late and out of order rather than holding other packets back.
- Replays of packets that had in fact arrived cost bandwidth until the duplicate is discarded; the volume is bounded by the 512-packet cap and the horizon, not measured.
- Suspicion is silence-based. A path that is alive but one-way (receives nothing, still delivers) is treated as suspect, and a briefly quiet healthy path with a slow probe interval could be flagged and then recovered; the thresholds were not tuned on a physical 5G/Starlink link.
- No live measurement and no server deployment exist for this change. Enable it on both ends only after validating against a physical interruption; it needs no server upgrade but the server benefits only if it enables it too.


## Throughput pinned near the start rate on a jittery link

Reported: a single ~105 Mbps link delivered roughly 1.5-10 Mbps. Live status (`.runtime/userspace-status.json`, one path up) showed the client's budget at 1.5-2.25 Mbps with only 2 growth steps, minimum RTT 23 ms against smoothed 60-85 ms, jitter 40-130 ms and a 270 ms spike. The second path was unavailable (Ethernet 3 had no IPv4 address and gateway), so this was a one-link measurement.

Cause (reproduced, not just inferred): the delay gate in `PathBudget.acknowledge` compared smoothed RTT with a **lifetime-minimum** RTT and no jitter allowance (`srtt - min_rtt > max(25 ms, 0.5*min_rtt)`). On a link whose best case is rare, that fires whenever the flow is backlogged, i.e. exactly when growth is wanted, and `delay_samples > 0` blocks additive and startup growth. With the budget stuck near 1 Mbps, the 100 ms bulk queue ages packets out, the inner TCP window collapses, and the flow never produces the evidence needed to grow. In a loopback emulation (40 Mbps bottleneck, 25 ms base RTT, up to 60 ms jitter each way, Reno-style source behind the configured 100 ms / 256-packet bulk queue) the old gate held the budget at 1.0 Mbps for 14 s with `delay_samples` stuck at 3.

Fix (Python `gamebond/bonding.py` and the Go mirror `native-edge/bond/budget.go`): the queue-delay estimate now uses a decaying baseline (minimum of the current and previous 10 s buckets) and requires queue delay to exceed `4 * rtt_var` (smoothed mean deviation) as well as the previous thresholds. A standing queue far above jitter still stops growth. `rtt_var_ms` is exposed in stats. Go vectors regenerated from Python (`tools/generate_native_budget_vectors.py`); Go and Python agree on all 94,607 operations. Regression tests: `test_rtt_jitter_alone_does_not_pin_a_backlogged_path_at_its_start_rate` (fails on the old gate) and `test_genuine_queue_growth_still_stops_growth`.

Not established: no physical measurement after the fix, and neither fix is deployed. Downloads are paced by the **server's** budget, so the server (195.154.119.136) must run the fixed code; a client-only restart improves upload only. Emulated delivery after escaping the pin follows the toy TCP source, not a 105 Mbps result. The 1 Mbps start (`bonding_initial_rate_mbps`) still costs a few seconds of ramp on every new path.
